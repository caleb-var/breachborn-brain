Environmental Foundation V1 — execution protocol

Authorized 26 November 2026. This operational protocol accompanies the full technical implementation plan and the progress record. It governs the user’s intended GPT-6.2 Very High/Extra High main local orchestration chat and two actual local implementation worker chats. Model naming and actual delegation capabilities depend on the available Codex interface; do not pretend to control another chat if the interface does not support it. No new engine code or test execution is claimed here.

Mission

Complete M0 preparation and every delivery milestone M1–M5 of the technical plan as one continuous full replacement. Deliver real integrated functionality, not a report-only pilot. The new implementation is the standard for fresh worlds; remove/disconnect superseded environmental mechanisms and legacy selection paths when the replacement is ready. Do not keep a second production water system, duplicate atmosphere, legacy compatibility layer, or old save conversion merely for continuity. Keep useful gameplay, Godot/Jolt, existing Zylann terrain integration, actual physical contracts, and historical evidence. Protect unrelated local changes, assets, user saves and installations.

Follow the current A–F package sequence in the active environment-only plan: fast reusable development baseline; terrain loading and continent-to-local rendering; water; weather; ongoing terrain evolution; integrated environmental evidence. These complete remaining M1–M5 rather than restart delivered work. All colony/actor/navigation/settlement work is out of scope, not merely population-scale qualification. Complete ecology, other liquids and unrelated legacy repair remain deferred.

Orchestrator and worker

  • Orchestrator: executes the user-approved end-to-end Brain plan, dependency manifest, sequence and integration boundaries; the user and planning chat retain fundamental architecture decisions. Read latest canonical Brain and actual worker receipts. Give the worker concrete bounded implementation packages with source pin, scope, acceptance, target paths if known, dependency order and commit/report expectations. Use independent implementation judgement, not micromanagement. Review exact diffs and evidence for changed paths, resolve routine issues, adjust reversible tunables, then immediately advance to next package/milestone. No request for approval simply because one package or milestone finishes.
  • Worker: owns actual code/build/edit work in the assigned checkout. Implement the selected existing algorithms and minimal native adapters; prefer reuse, simple data structures and physical consistency. Make necessary related call-site changes and remove superseded paths rather than preserve old environmental architecture. Perform only the directly useful checks, fix local issues within scope, record actual results and report the exact code commit, changed capabilities, incomplete requirements, checks, costs and any real blocker. Return work that runs where feasible, not pseudocode or fixture-only substitution. Do not invent a new solver or change fundamental architecture, requirement or scope without explicit user approval.
  • One writer per checkout. Orchestrator is accountable for canonical documentation and publication; worker supplies evidence and may author assigned docs when ownership is explicitly handed off. Coordinate via commits and the durable progress record, not duplicated work. Use actual local Codex chats, not subagents. Verify that the interface supports creating, messaging and receiving returned messages from those chats. If that mechanism is unavailable, report the limitation and provide two self-contained worker handoffs for the user to start/return; do not substitute subagents, invent a chat API or claim a message was sent. A separate chat does not automatically receive messages or keep running merely because another chat has been prompted.
  • Continue across all milestones within available execution sessions. If a context/session boundary occurs, save a precise continuation with the next executable package, current commit and real open issue; do not claim background execution or completion. Neither agent stops for routine design choices, optimization tradeoffs within the accepted architecture, ordinary builds/fixes or milestones. Do not create automated infinite loops or repeat failed attempts without changing the diagnosis.

Implementation-first verification

Minimum purposeful verification, not zero verification. Use the same small connected world and concise directly relevant checks for changed numerical/geometry behavior. Reuse upstream tests where useful, without reproducing all scientific benchmarks. Use the cheapest relevant execution mode of the one permanent environment baseline; native checks need no Godot launch. Launch the shared Godot scene for changed rendering/streaming or engine integration, not every package. Use quick targeted profiling and representative combined scale/visual checks at M5, with enough repeat/diagnostic detail to make measured claims meaningful. Run additional checks only to diagnose a consequential failure. Prefer fixing the feature over writing a large verification framework. Do not run exhaustive old regression suites, full legacy compatibility campaigns, performance matrices for every candidate, or repair unrelated failing tests. Keep Brain’s normal automated validation and safe publication; it is not a competing physics campaign.

Do not waive finite water/heat exchanges, sealed-barrier correctness, meaningful downstream consequences, current geometry, offscreen progression, persistence and actual weather. Preserve honest units/clocks and evidence. A playable approximation is appropriate; scientific forecast precision is not the goal. Do not label performance, scale or unexecuted functionality as passed. Historical targets and proposed acceptance tolerances remain as in the technical plan; choose meaningful local tolerances before checking, not after failure. If target hardware unavailable, say so and continue other implementable work; don’t block every feature on exhaustive target certification.

Stop and escalate only when necessary

Escalate if the primary upstream method is fundamentally unsuitable, a substantial bespoke numerical solver would be required, a hard physical requirement or performance envelope cannot be achieved without a product tradeoff, a material dependency/license change or fundamental clock/gameplay choice needs approval, or real permission/hardware/access/safety constraints make further meaningful work impossible. First make a bounded diagnosis and attempt the smallest compatible fix; do not spend days on circular tuning. Continue independent unblocked work where sensible. Report: exact failure or conflict, evidence, what has been tried, impact on the plan, one recommended path, and the precise decision or research question. Do not stop simply to ask for routine confirmation. Do not suppress the blocker to mark a milestone complete.

Two-repository workflow

  • Canonical private repo: https://github.com/caleb-var/godot_aokana. Inspect actual HEAD, nested AGENTS, local ownership and remote state. Create a reviewable implementation branch/worktree from appropriate runtime source head, synchronize the active V1 plan/authorization, commit coherent code changes and push for review. New runtime becomes the default fresh-world implementation on this branch; use normal repository merge controls rather than force-push or overwrite unrelated work.
  • Canonical authored documentation resides under docs/brain/content/ in the same private repo. The authorized publication ref is docs/breachborn-brain-refresh-20261125. Keep this ref current via a dedicated documentation worktree or controlled small docs-only commits based on its latest head. Reflect relevant records in the implementation branch as needed; do not merge unrelated runtime changes onto the docs branch. Avoid parallel writers and reconcile automatic generated-index commits before each update. Use stable IDs/typed edges, preserve existing records and historical negative evidence. Update affected systems, contracts, candidate selection/status, requirements traceability, and the V1 progress record after each meaningful package/milestone. Keep intent/selected/implemented/verified separate and cite exact source/code revision.
  • Public generated repo: https://github.com/caleb-var/breachborn-brain, main; live site https://caleb-var.github.io/breachborn-brain/. Never manually edit public generated files, copy private code/history/saves, or expose credentials or confidential local details. Author canonical Markdown, run python docs/brain/tools/atlas.py --write, python docs/brain/tools/atlas.py --check and python docs/brain/tools/test_brain.py when available, then commit/push the authorized docs ref. Use the cached local publication procedure in Brain workflow and docs/brain/tools/publish_local.py --publish. Do not spend private Actions minutes on ordinary edits. Confirm exact source and generated mirror revisions and deployed public source marker after meaningful publication; if publication fails or lags, use current canonical records and report the lag. Never bypass publication safety. Do not wait on routine asynchronous publication before implementing the next independent package. A failed mirror publication does not erase canonical progress.
  • Do not expose private source snippets, logs, filesystem details, or sensitive user data in publicly authored records. Keep detailed private runtime evidence outside docs/brain/content/ where necessary and publish safe summaries and reference identities.

Progress and completion

Provide concise progress receipts at integrated packages and every milestone, without waiting for a user reply: completed/working, exact commits, changes from plan, directly relevant checks and measured/estimated distinction, unresolved issue, documentation commit and mirror status, next work. Persist them in the progress record and relevant canonical system records. Use one lightweight status record, not a custom orchestration platform.

Final report: implemented M1–M5 capability status, actual default-path replacement, remaining known limitations, measured scale/CPU/GPU/RAM/debt and visual evidence where available, commits/PRs, dependency notices and canonical Brain publication state. Do not call an unfinished or unmeasured implementation complete. The user wants maximum implementation, not maximum paperwork.
